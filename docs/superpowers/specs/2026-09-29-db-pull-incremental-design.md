# db:pull 증분 동기화 — 설계

> 작성 2026-09-29 · 상태: 설계 승인 대기(사용자 검토) · 브랜치 `feat/db-pull-incremental`
> 관련: [05-data-infra](../../status/05-data-infra.md) · [pipeline_guide.md](../../pipeline_guide.md) · TODO **T-014**
> 설계 합의: 2026-09-27 세션(①접근·②동작·③곁들임 3단계 합의)

## 1. 목적

`npm run db:pull`이 매번 Supabase의 53만 행을 **통째로** 다시 받는다. 바뀐 것이 며칠치뿐인
평일에도 전량을 받는다. 바뀐 날짜만 받아 적재하도록 바꾼다.

**비목표:** 미러에 쓰기(미러는 읽기 전용 유지) · 실시간 동기화 · REST 폴백 경로의 증분 ·
원천 스키마 변경(`updated_at` 컬럼 추가 등) · 병렬 적재.

## 2. 지금 무엇이 비싼가 (측정)

| | 값 |
|---|---:|
| 총 행수 | 약 53만 (`training_logs` 376,372 · `race_entries` 88,593 · `predictions` 43,940 · 나머지 약 2.6만) |
| DB 왕복 | 약 545회 (1000행 페이지네이션) |
| `OFFSET` 재스캔 누적 | 약 **7,100만 행** (`training_logs` 377페이지의 평균 offset 18.8만) |

**돈 문제가 아니다.** `DATABASE_URL` Postgres 직결은 Supabase egress 과금과 무관하다
([05-data-infra](../../status/05-data-infra.md) 기록). **시간** 문제다.

그리고 비용의 주범은 "전량"이 아니라 **페이징**이다. `LIMIT/OFFSET`은 PostgREST의 1000행
상한을 넘기려고 도입된 REST용 제약인데, 직결 경로가 그대로 물려받았다. `OFFSET`은 건너뛸
행을 매번 처음부터 세고 버리므로 같은 데이터를 약 190배로 훑는다.

## 3. 결정 사항 (사용자 합의 2026-09-27)

1. **직결 경로에서 페이징을 없앤다.** 커서/단일 쿼리로 한 번에 받는다.
2. **증분 판정은 "날짜별 내용 해시"로 한다.** 행수만 세면 착순 채워짐·일괄 정규화를 놓친다.
3. **비교는 "원천 지금 vs 원천 그때"** — 미러에서 해시를 재계산하지 않는다(§5.2, 가장 중요).
4. 적재는 **한 트랜잭션**에 `DELETE → INSERT → 지문 갱신`.
5. 전량 전환 규칙을 두고, **스키마 변경은 자동으로 전량**이 되게 한다.
6. 판단 로직을 **DB 없이 테스트되는 순수 함수**로 분리한다(B안 채택, A안 기각).
7. 곁들임 3개: 미러 신선도 경고 · 파일 잠금 원인 안내 · 빠진 테이블 2개 추가.

### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 원천에 `updated_at` + 트리거 추가 | 날짜 지문으로 충분. 53만 행 백필과 모든 쓰기 경로 영향 검토가 따라붙는다 |
| 행수 + 핵심 컬럼 몇 개만 비교 | 착순 채워짐은 잡아도 예상 못 한 일괄 수정(016 `hr_name` 정규화 같은)을 놓친다. 지금 고치려는 문제와 같은 종류 |
| 최근 N일 고정 윈도우 | 그보다 오래된 과거가 바뀔 때(백필·재학습·정규화) 사람이 기억해서 전량을 돌려야 한다 |
| 스크립트 한 파일에 전략 분기(A안) | 판단 로직이 DB 연결과 뒤섞여 테스트 불가. 이 일의 위험은 "적재 실패"가 아니라 "바뀐 걸 안 바뀌었다고 오판" |

## 5. 증분 한 판의 동작

### 5.1 지문 조회 (테이블당 쿼리 1회)

```sql
SELECT race_date AS d,
       count(*)  AS n,
       md5(string_agg(t::text, '|' ORDER BY meet, rc_no, pthr_no)) AS h
FROM race_entries t
GROUP BY race_date
```

- `t::text`는 행 하나를 통째로 문자열로 편 것이라 **어느 컬럼이 바뀌어도 해시가 달라진다.**
- 정렬 키는 §4 표의 "PK 나머지". 순서가 흔들리면 내용이 같아도 해시가 달라지므로 **고정 필수**.
- 돌아오는 양은 날짜당 1줄(`race_entries` 약 1,000줄). `n`은 판정에 쓰지 않고 로그·진단용.

### 5.2 ⚠️ 비교 축 — 이 설계의 핵심

**미러에서 해시를 재계산하면 절대 작동하지 않는다.** 해시는 행을 문자열로 편 결과에 걸리는데
Postgres와 DuckDB는 같은 행을 다르게 쓴다(숫자·날짜·jsonb 표기). 모든 날짜가 영원히 "바뀜"으로
나와 매번 전량을 받게 된다.

→ **원천 지문을 받을 때 `_sync_state`에 그대로 저장하고, 다음 pull에서 "원천 지금 vs 원천 그때"를
비교한다.** 미러는 해시를 계산하지 않는다. 양쪽 표기 차이 문제가 통째로 사라진다.

부작용: 미러 파일을 사람이 직접 고치면 감지 못 한다 → 미러는 읽기 전용이므로 수용한다.

### 5.3 `_sync_state` 스키마 (미러 안, DuckDB)

```sql
CREATE TABLE IF NOT EXISTS _sync_state (
  table_name  VARCHAR NOT NULL,   -- 'race_entries'
  date_key    BIGINT  NOT NULL,   -- 20260920 (날짜 키 값 그대로)
  row_count   BIGINT  NOT NULL,   -- 진단용
  hash        VARCHAR NOT NULL,   -- 원천이 준 md5
  synced_at   TIMESTAMP NOT NULL, -- 이 날짜를 마지막으로 적재한 시각(UTC)
  PRIMARY KEY (table_name, date_key)
);
```

전량 테이블은 `date_key = -1` 한 줄로 "마지막 전량 적재 시각"만 남긴다(신선도 판정 §7.1에 사용).

### 5.4 판정

| 원천 | 저장된 지문 | 판정 |
|---|---|---|
| 있음 | 해시 같음 | 건너뜀 |
| 있음 | 해시 다름 | **바뀜** → 재적재 |
| 있음 | 없음 | **신규** → 재적재 |
| 없음 | 있음 | **사라짐** → 삭제 |

날짜 안에서 일부 행만 지워진 경우도 해시가 달라져 "바뀜"으로 잡히고, 재적재가 삭제 후 삽입이라
정확히 반영된다.

### 5.5 적재 (한 트랜잭션)

```
원천:  SELECT * FROM race_entries WHERE race_date = ANY($1)   ← 왕복 1회, 페이징 없음

미러:  BEGIN
         DELETE FROM race_entries WHERE race_date IN (<바뀜 ∪ 사라짐>)
         INSERT INTO race_entries BY NAME SELECT * FROM read_json_auto('<tmp>')
         DELETE FROM _sync_state WHERE table_name = 'race_entries' AND date_key IN (...)
         INSERT INTO _sync_state ...   -- 바뀜/신규 날짜의 지문 (사라짐은 넣지 않음)
       COMMIT
```

- **`BY NAME`** — 컬럼 위치가 아니라 이름으로 맞춘다. 지금처럼 `CREATE TABLE AS`로 매번 새로
  만들 때는 문제없던 것이, 증분에선 컬럼 순서가 어긋나면 값이 엉뚱한 칸에 들어간다.
- **지문 갱신을 같은 트랜잭션에 묶는 것이 핵심.** 중간에 끊기면 데이터도 지문도 함께 롤백돼
  다음 pull이 같은 날짜를 다시 시도한다.
- **불변식:** *미러의 내용은 항상 `_sync_state`의 지문이 말하는 상태와 일치한다.* 반쯤 반영된
  상태가 존재할 수 없다.

### 5.6 전량 전환

다음 중 하나면 지금과 같은 `DROP TABLE` + `CREATE TABLE AS` 경로로 간다.

1. 미러에 그 테이블이 없음 (첫 실행)
2. `_sync_state`에 그 테이블 지문이 하나도 없음
3. **바뀜 ∪ 사라짐 날짜 수가 원천 날짜 수의 절반 초과**(`FULL_RELOAD_RATIO = 0.5`) — 날짜별
   지우고 넣기보다 통째가 빠름
4. `--full` 플래그
5. `DATABASE_URL` 없음(REST 폴백) — 해시 집계가 SQL이라 지문 자체를 못 받음

전량 경로도 끝나면 §5.1 지문을 받아 `_sync_state`를 채운다(다음 pull부터 증분).
**단 사유 5(REST 폴백)는 예외** — 지문 SQL을 실행할 수단이 없으므로 `_sync_state`를 건드리지
않는다. 이미 있던 지문(지난 직결 pull 시점의 것)은 지우지 않고 그대로 둔다.

> 이때 지문은 "지난 직결 pull 시점의 원천"을 가리키는데 미러 내용은 "지금 원천"이라 §5.5의
> 불변식이 잠시 깨진다. **틀린 답이 나오지는 않는다** — 비교는 언제나 *원천*을 상대로 하므로,
> 그 사이 바뀐 날짜는 다음 직결 pull에서 "해시 다름"으로 잡혀 다시 받는다. 이미 최신인 날짜를
> 한 번 더 받는 낭비만 생기고, 갱신을 놓치는 일은 없다. 지문을 지우는 선택(다음 pull이 전량)도
> 맞지만 더 비싸서 택하지 않는다.

이 경로로만 돌리면 미러는 영영 전량이며, 그게 의도된 동작이다.

> **딸려오는 성질:** 원천에 컬럼이 추가되면 `t::text`가 바뀌어 **모든 날짜 해시가 달라지고**
> 규칙 3에 걸려 자동으로 전량이 된다. 스키마 변경 감지 코드가 따로 필요 없다.
> 반대로 Postgres 업그레이드 같은 표기 변화로도 전량이 돌 수 있는데, 전량은 정확성 쪽으로
> 안전한 실패라 수용한다.

## 6. 모듈 구조 (B안)

```
src/db/mirror/
  tableSpecs.ts    테이블별 전략 표 (full | incremental + dateCol·orderCols)
  fingerprint.ts   지문 SQL 생성 + 지문 비교(순수)
  syncPlan.ts      비교 결과 → SKIP | INCREMENTAL(dates) | FULL 결정(순수)
  syncState.ts     _sync_state 읽기·쓰기 + 신선도 판정
scripts/sync_local_db.ts   CLI 껍데기: 연결·계획 실행·출력
```

핵심 판단(무엇이 바뀌었나 · 전량으로 갈아탈까 · 미러가 묵었나)이 전부 DB 없이 테스트되는
순수 함수가 된다. 실제 적재만 임시 DuckDB로 통합 테스트한다.

## 7. 곁들임 3개

### 7.1 미러 신선도 경고

`getLocalDb()`(`src/db/localDb.ts`)가 지금은 "파일 없으면 에러"만 본다. `_sync_state`의
`max(synced_at)`을 읽어 임계(**기본 3일**) 초과면 **stderr 경고만** 낸다.

> **왜 3일인가:** 경마가 금·토·일 중심이라 7일로 잡으면 *주말 하나를 통째로 놓쳐도 조용하다.*
> 3일이면 일요일 경주 뒤 수요일에는 반드시 경고가 뜬다. 상수 하나(`MIRROR_STALE_DAYS`)로
> 두고, 실사용에서 시끄러우면 올린다.

```
⚠️ 미러가 79일 묵었습니다 (마지막 db:pull: 2026-07-10)
   최신 결과가 필요하면 npm run db:pull 먼저 실행하세요
```

**막지 않는다.** 백테스트·게이트 실험은 일부러 과거 데이터로 돌리는 일이 많다. 판정은 순수
함수(`mirrorAgeDays` → 경고 문구), 끄기는 환경변수. `_sync_state`가 없으면(구 미러) 경고 생략.

> 2026-09-27에 79일 묵은 미러로 O-004를 판정할 뻔한 자리를 막는 장치다.

### 7.2 파일 잠금 원인 안내

DuckDB는 writer가 하나뿐이고 이 저장소는 워크트리를 여러 개 쓴다. 지금은 원인을 알 수 없는
IO 에러로 죽는다 → 원인과 대처를 말하는 메시지로 감싼다. **재시도·대기는 넣지 않는다**(상대가
언제 끝날지 모르는데 조용히 기다리면 더 헷갈린다).

⚠️ **함정 — 범인은 남이 아닐 수 있다.** 2026-09-27에 두 번 다 자기 자신이었다.
- `getLocalDb`의 비동기 싱글턴 경쟁(고침 `71f8f00`) — 동시 호출이 같은 파일을 두 번 열었다.
- `db:pull` 프로세스가 **"완료" 출력 뒤에도 잠깐 파일을 쥔다**(`close()` 미지원 → GC).
  직후 다른 명령을 이어 돌리면 실패한다.

메시지에 **에러가 가리키는 PID가 자기 자신일 수 있다**는 점을 넣는다(PID가 실행마다 다르면
남이 아니라 자기 프로세스다).

### 7.3 빠진 테이블 2개

`combo_dividends`·`shadow_predictions`를 `TABLES`에 추가(§4). 조합배당은 경주당 수백~수천 행
(11두=1,375개)이라 증분 이득이 큰 축이다.

## 8. 값 모양 보존 (2026-09-27 사고 반영)

**미러는 supabase-js와 같은 값 모양을 돌려줘야 한다.** 안 지키면 에러 없이 조용히 틀린다.

실제 사고(`68402b9`): `read_json_auto`가 만든 `TIMESTAMP`가 `DuckDBTimestampValue{micros}`
객체로 새어 `Date.parse`→NaN → `isLivePrediction`이 전 행을 "백필"로 떨궈 **O-004 판정이 0행**.
지금은 `unwrapDuck`이 ISO 문자열로 바꾼다.

증분은 `read_json_auto` 추론에 **더** 의존하므로(매번 부분 JSON을 읽는다) 다음을 지킨다.

1. **추론 흔들림 차단** — 증분 INSERT는 이미 있는 테이블에 `BY NAME`으로 넣으므로 대상 컬럼
   타입은 **기존 테이블이 결정**한다. 부분 JSON의 추론 결과가 테이블 타입과 다르면 DuckDB가
   캐스팅하거나 실패한다. **실패하면 그 테이블을 전량으로 폴백**하고 경고를 남긴다
   (조용히 넘어가지 않는다).
2. `TIMESTAMPTZ`가 JSON 경유로 `TIMESTAMP`로 굳는 현재 동작은 **바꾸지 않는다**(값은 UTC,
   `unwrapDuck`이 Z를 붙여 흡수). 이 스펙의 범위 밖이되 문서에 남긴다.
3. 통합 테스트에 **시각·jsonb 컬럼이 증분 적재 후에도 같은 모양인지** 확인하는 케이스를 둔다.

## 9. 테스트

| 층 | 대상 | 방식 |
|---|---|---|
| 순수 | 지문 비교 → 바뀜/사라짐/그대로 | DB 없이 단위. **여기가 위험의 본체** |
| 순수 | 전량 전환 규칙 5가지(첫실행·지문없음·절반초과·`--full`·REST) | 경계값 포함 |
| 순수 | 신선도 판정(임계·`_sync_state` 없음) | |
| 스냅샷 | 테이블별 지문 SQL 생성 — 정렬 키가 §4 표와 일치 | |
| 통합 | 임시 DuckDB 적재 → 한 날짜만 바꿔 재적재 → **그 날짜만 바뀌고 나머지 불변** | Postgres 불필요 |
| 통합 | 날짜 삭제 반영 · 트랜잭션 롤백 시 지문 미갱신 | |
| 통합 | 시각·jsonb 컬럼이 증분 적재 후에도 같은 모양(§8) | |

TDD: 테스트 먼저 → 실패 확인 → 구현. 기존 `src/db/localDb.test.ts` 옆에 둔다.

## 10. 작업 순서 (계획 단계에서 태스크화)

1. `tableSpecs.ts` — 전략 표 + §4 값
2. `fingerprint.ts` — SQL 생성 + 비교(순수, 테스트 먼저)
3. `syncPlan.ts` — 전량 전환 규칙(순수, 테스트 먼저)
4. `syncState.ts` — `_sync_state` CRUD + 신선도 판정
5. `sync_local_db.ts` 재배선 — 페이징 제거 + 증분/전량 분기 + 빠진 테이블 2개
6. `localDb.ts` — 신선도 경고 · 잠금 메시지(§7.1·7.2)
7. 통합 테스트 · 실제 `db:pull` 2회 실행 검증(1회차 전량+지문, 2회차 SKIP)
8. 문서 갱신 — `docs/pipeline_guide.md`(명령·동작) · `docs/status/05-data-infra.md`

## 11. 검증 기준 (끝났다고 말할 조건)

- 바뀐 게 없을 때 **지문 쿼리 5회만 돌고 아무 행도 받지 않는다**
- 한 경주일이 바뀌면 그 날짜 행만 받아 적재하고, 다른 날짜의 행은 건드리지 않는다
- 전량 1회 → 증분 1회 실행 후 **모든 테이블 행수가 원천과 일치**
- 전체 테스트·타입체크 통과

## 12. 위험

| 위험 | 대응 |
|---|---|
| 지문 정렬 키가 PK와 어긋나 해시가 매번 바뀜 | 스냅샷 테스트로 고정(§9) |
| 부분 JSON 타입 추론이 테이블 타입과 불일치 | 실패 시 전량 폴백 + 경고(§8.1) |
| `_sync_state`만 갱신되고 데이터는 안 들어간 상태 | 한 트랜잭션으로 묶어 원천 차단(§5.5) |
| 큰 `IN (...)` 목록으로 쿼리가 비대해짐 | 날짜 수가 절반을 넘으면 전량으로 가므로 상한이 걸린다 |
| 증분이 오히려 느려지는 경우(대부분 바뀜) | 절반 규칙이 전량으로 돌린다 |
