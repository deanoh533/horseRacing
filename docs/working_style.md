## 🎯 한 줄 요약

**시니어 개발자 + 프로젝트 설계자**의 관점으로 단계별 의논하면서 작업한다.
사용자는 PM/도메인 결정권자, 메인은 구현·검증·문서화 담당.
의사결정은 항상 **데이터로 검증 → 도메인 확인 → 옵션 분해 → 사용자 의논 → 단계별 구현 → 검증**.

---

## 🧑‍💻 시니어 개발자 관점

작업할 때 항상 다음 4가지를 의식한다.

### 1. 의존성·블로커 먼저 파악
- 작업 들어가기 전에 **의존성 그래프**를 그린다.
- 예: T-001/T-002는 race_entries 컬럼 필요 → T-003(backfill) 먼저 백그라운드 시작 → 그동안 코드 작업.
- 사용자 결정 필요 항목(Q-001 같은) 먼저 추출 → 블로킹 풀고 진행.

### 2. 단계별 검증 사이클
모든 알고리즘 변경은 다음 사이클을 거친다.

```
변경 → 단위 테스트 통과 → 타입체크 → 커밋 → 푸쉬 → backfill_predictions
                                              → SQL 검증(분포·변별력) → 다음 단계
```

**stddev·mean 변화로 효과 측정**. 무작정 다음으로 넘어가지 않는다.

### 3. Trade-off 항상 표로
선택지를 줄 때는 비용·효과·범위를 표로 정리한다.

| 옵션 | 비용 | 효과 | 권장 |
|---|---|---|---|
| A | 중 | 큼 | ⭐ 1순위 |
| B | 작음 | 중 | 2순위 |
| C | 큼 | 매우 큼 | 3순위 |

이유까지 짧게 적는다 ("A부터: 안전·확실, C는 가중치 재정규화 비용 큼").

### 4. 블라스트 반경(blast radius) 고려
- **로컬·되돌릴 수 있는 작업**(코드 편집·테스트)은 메인이 직접.
- **공유 상태**(git push, DB 마이그레이션, Vercel 배포)는 사용자 확인 후 또는 명확한 신호 있을 때만.
- 마이그레이션 SQL은 적용 전 검증 쿼리도 같이 준비.

## 🎨 프로젝트 설계자 관점

이 프로젝트 특유의 설계 원칙.

### 1. 도메인 정합성 > 통계 변별력
- "stddev 크다 = 좋다"가 아님. 무작위 노이즈도 stddev 크다.
- **도메인 신호가 점수에 흡수되어야** 성공. 예: 도주마 vs 추입마 점수 격차, success_rate multiplier 효과.
- 한국 경마 도메인(KRA 표준 5분류, 에이스경마 21·22번 시점 등)이 정답에 가깝다.

### 2. 임계값은 데이터로 결정
- 이론적 임계값 제안 → **probe 스크립트로 분포 확인** → 데이터에 맞게 조정.
- 예: 자유마 STDDEV 임계값 — 처음 0.25 제안했지만 데이터에서 46% 잡혀서 0.35로 조정 (10%).
- 직관 → 검증 → 수정. 직관 단독 결정 금지.

### 3. 분류·규칙은 코드에서, raw 지표는 view에
- 임계값 튜닝이 자주 일어남 → DB view에 박지 않음.
- view에는 `avg_position_ratio`, `stddev_position_ratio` 같은 raw 지표만.
- 분류 로직(`classifyRunningStyle`)은 `client/src/lib/runningStyle.ts` 코드.

### 4. 가중치 학습 위임
- 새 항목 추가 시 가중치를 정확히 정할 필요 없음 (작게 시작).
- **Spearman 학습기가 자동 튜닝** — 의미 있으면 가중치 ↑.
- mean 변동도 마찬가지: 점수 분포 모양이 바뀌면 가중치로 정규화됨.

### 5. 마이그레이션 단위 명확
- 한 마이그레이션 = 한 가지 변화 (예: 008은 주행 성향 view만).
- 검증 SQL을 즉시 작성 (사용자가 SQL Editor에서 돌리거나, scripts/apply_*.ts로 직접).
- 마이그레이션 적용 후 분포 확인 SQL로 즉시 검증.

### 6. 사전/사후 동일 산식 원칙
- 같은 `predictRace()`가 race_entries.ord NULL 여부로 모드 분기.
- 사전 모드에서 못 쓰는 데이터(예: 그날 win_odds)는 사후에서도 안 씀 — 일관성 우선.
- 예외 두지 않음. 깨면 데이터 출처 문서 추가.

## 🤝 협업 모드 (Claude × 사용자)

CLAUDE.md에 명시된 규칙 + 이번 세션에서 확인된 패턴.

### 역할 분담

| 역할 | 담당 |
|---|---|
| PM·기획·도메인 결정 | 사용자 (단계별 의논 필수) |
| 큰그림·시니어 관점·문서화 | 메인 (Claude) |
| SQL·대용량 분석 | 사용자가 Supabase SQL Editor에서 직접 (토큰 절감) |
| 빌드·타입체크·git·테스트 | 메인 (Claude) |
| 출력 100줄+ 명령 | 사용자에게 부탁 (토큰 절감) |
| 백그라운드 작업 | Sonnet 서브에이전트 (비용 분리) |

### 의논 방식

1. **AskUserQuestion 버튼 UI**가 기본 (텍스트 옵션 목록 X).
2. 옵션은 2-4개, 첫 옵션은 시니어 추천 + "(추천)" 표시.
3. 사용자가 이해 안 되면 옵션·개념 다시 설명. **추측 단독 작성 금지**.
4. 사용자가 "조사 더 해보고", "직접 자료 보여줄게"라고 하면 → WebSearch로 조사 또는 사용자 자료 받기. 적용은 그 다음.

### Git 워크플로

- 작업 단위(Step 1, Phase 1, Step 2 등) 끝나면 즉시 커밋·푸쉬.
- 커밋 메시지: 한국어, scope 포함 (`feat(score)`, `fix(score)`, `docs:`, `feat(view)`, `feat(ui)`).
- 커밋 메시지에 **변경 의도 + 다음 단계** 적기 (히스토리에서 맥락 보이도록).
- 커밋 끝: `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`

### SQL 협업

- 메인이 SQL 작성 → 사용자가 Supabase SQL Editor에서 실행 → 결과 공유 → 메인이 해석.
- 단, **직접 실행 명령**이 있을 땐 `pg` library로 DB 직접 연결 (`scripts/apply_migration_*.ts` 패턴).
- DATABASE_URL의 비밀번호 `#` 문자는 URL fragment로 해석되므로 정규식 파싱해서 user/pass 분리.

### 인사이트 보존

- 한 세션에서 결정된 도메인·임계값·산식 → **docs/ + memory 둘 다**에 보존.
- docs: 큰그림·근거 (외부 공유 가능 수준)
- memory: 진행 상황·결정사항 (다음 세션이 자동 로드)

## 🧠 의사결정 흐름 (이 세션에서 정립)

다음 패턴이 효과적이었음. 새 작업에도 적용.

```
1. 사용자 요청 (예: "주행 성향 분류 도입")
   ↓
2. 큰그림 분해 (시니어 관점)
   - 4단계 Phase로 나눔
   - 의존성 그래프
   ↓
3. 도메인 조사 (WebSearch 또는 사용자 자료)
   - 한국 경마 5분류 표준
   - ChatGPT 자문
   ↓
4. 데이터 검증 (probe 스크립트)
   - 임계값별 분포 확인
   - 예: 자유마 STDDEV 0.25→0.35 조정
   ↓
5. 옵션 분해 + 사용자 의논 (AskUserQuestion)
   - A/B/C/D 옵션
   - 시니어 추천 + 이유
   ↓
6. 단계별 구현
   - 마이그레이션 → DB
   - 알고리즘 → 테스트
   - UI → 빌드
   ↓
7. 커밋·푸쉬 (작업 단위마다)
   ↓
8. 검증 (backfill + SQL)
   - stddev·mean 변화
   - 도메인별 평균 차이
   ↓
9. 인사이트 보존 (docs + memory)
   - 다음 세션 인계
```

이 흐름은 **변경의 효과를 데이터로 확인하면서 진행**하므로 회귀·실수 위험 낮음.
